# OpenJDK 28+13 方法静态复用与路径入度分布

## 摘要

本研究在 OpenJDK `jdk-28+13` Java 类库的静态方法调用图上，以
Veldhuizen（2005）“Reuse and Zipf's Law”的计算口径统计每个 method
node 收到的字节码静态引用次数，并与直接+间接路径入度比较。完整图包含
239,765 个方法节点、620,634 个不同调用 pair 和 859,406 个调用位置。

按论文口径，138,981 个方法至少收到一次引用。将方法按静态引用次数降序
排列后，完整正值总体的经验 rank 指数为 `β=0.953`，固定 `1/r` 模板在
log10 空间达到 `R²=0.970`、`RMSE=0.073 decades`。因此 OpenJDK 方法的
直接静态引用分布与论文所述 Zipf 形状高度一致。

作为另一项结构分析，138,981 个节点具有正路径入度，100,784 个节点的路径入度为零，3,810
个节点构成循环终止边界。最大路径入度为
6,919,543,454,663,852。正值总体的 rank–frequency 指数估计为
`β = 3.523`，显著偏离 Zipf 定律的 `β = 1`。素数倒数模板的固定形状
误差略低于 Zipf 模板，但二者均不能充分解释经验曲线；该差异不构成
路径分布具有质数生成机制的证据。

## 论文对齐的复用计算

论文在 Unix 安装中遍历 executable objects 与 shared objects，统计每个
library subroutine 被静态引用的次数，按引用次数降序排列，然后在双对数
坐标绘制 rank `n` 与 `number of uses`，并叠加 `c·n^-1` 参考线。

本研究的一一映射为：library subroutine 对应 JVM method declaration；
静态 subroutine reference 对应指向目标方法的已解析 bytecode invocation
call site；方法 `v` 的 reuse count 为 `U(v)=Σ_u m(u,v)`。其中
`m(u,v)` 是 caller→callee pair 上的调用位置数。此处只计算直接引用，
不做传递闭包，也不把 caller 的路径数带入。

| 总体 | 数值 |
| --- | ---: |
| 全部方法 | 239,765 |
| 至少被引用一次的方法 | 138,981 |
| 静态引用总数 | 859,406 |
| 仅被引用一次的方法 | 69,646 |
| 单一方法最大引用数 | 20,608 |

完整正值总体的自由指数拟合为 `β=0.953`；固定 Zipf 模板的
`R²=0.970`、`RMSE=0.073 decades`，后者约等于 `10^0.073=1.18` 倍的
典型乘法误差。最高 1% 范围的 `β=0.887`、固定 Zipf `R²=0.982`、
`RMSE=0.051 decades`。69,646 个 singleton methods 形成尾部台阶；论文
也将大 rank 处的台阶归因于大量仅有少量引用的 subroutines。

论文的 Linux 数据还包括 x86 machine instructions；SunOS 与 Mac OS X
因缺少这类高频组件而将 rank 起点调整为 `n=50`。OpenJDK 曲线从 `n=1`
开始，不使用 offset，因为整个语料始终采用 method 这一种组件单位，没有
相应的遗漏高频类别。`β`、R² 与 RMSE 是本研究为量化拟合补充的诊断量；
论文 Figure 1 本身未报告这些统计量。

### 论文中的素数：理论类比而非生成机制

准确地说，论文使用了素数概念，但没有建立或设计新的素数分布。素数主要
用于提出四组理论类比：

| 数论侧 | 软件复用侧 |
| --- | --- |
| 素数无限多 | 有用软件组件可能无限多 |
| 素数作为整数因子的频率 | 组件在程序中的复用频率 |
| 第 `n` 个素数的大小 | 第 `n` 个组件的规模 |
| 整数所含素因子的数量 | 程序使用的组件数量 |

论文真正拟合和讨论的组件复用频率是

```math
\lambda(n) \approx \frac{c}{n},
```

即 Zipf-like 复用分布。素数分布在这里主要是理论类比和研究灵感，不是
软件复用模型的直接生成机制。因此，本报告路径分析中的 `1/p_r` 是额外
加入的负对照，而不是论文提出的组件复用模型；即使它对某一经验曲线的
误差更低，也不能据此推断软件复用由素数规律生成。

### 论文主要结论与 OpenJDK 统计的比较

| 论文结论 | OpenJDK 28+13 证据 | 判断 |
| --- | --- | --- |
| 组件按使用频率排序后呈 `λ(n)≈c/n` 的 Zipf-like 曲线。 | 138,981 个被引用方法的经验 `β=0.953`；固定 `1/r` 的 `R²=0.970`、`RMSE=0.073 decades`。 | 支持 |
| 程序员追求更短的代码，使库朝最大熵配置演化；Zipf 曲线是这种压力的结果。 | JDK 数据复现了曲线形状，但单次观察性快照不能区分最大熵、API 设计惯例、代码生成或其他形成机制。 | 形状一致，机制未验证 |
| 问题域熵参数 `H` 限制复用潜力：最多约 `1−H` 的代码可来自库；`H` 越低，越可能出现强复用。 | 调用引用数不包含未压缩程序大小、组件带来的代码节省或问题域程序分布，不能从当前 graph 反推 `H`。 | 不可由本数据检验 |
| 任何有限库都不完备；随着问题域扩展，总会存在更多能缩短程序的有用组件。 | Phase 4 的 5/5 个 package 留出折均发现正净节省 opcode macro；Phase 5 从 JDK 17 到 28 观察到 method 净增 16,967，且保留 caller 已调用新增组件。 | 有限、探索性支持；无限性未证明 |
| 组件规模、使用次数与标识成本受理论界限约束；程序使用的组件数量可能呈 Erdős–Kac 式正态行为。 | Phase 3 的条件组件数 skew=0.660、excess kurtosis=1.472、Q–Q R²=0.975，未通过预注册正态判据。Phase 4 的 use–size Spearman ρ=-0.011。 | 正态近似不支持；界限仅代理检验 |

综合而言，OpenJDK 结果为论文最直接的经验命题——“库组件的静态引用
频率近似 Zipf”——提供了新的 Java 类库证据，但不构成对论文全部信息论
与 Kolmogorov complexity 结论的验证。路径入度的经验 `β=3.523` 进一步
说明：把 reuse unit 从直接静态引用改为传递路径组合，会得到显著更陡的
分布；指标定义决定了结果能否与论文比较。

## Phase 2–5：理论命题检验

Phase 1 的单快照 vocabulary saturation curve 被跳过，因为 Phase 4 直接
测试留出数据是否仍存在能缩短描述的新片段，Phase 5 直接观察跨版本组件
增长；这两项对“有限库不完备”的经验含义更强。

### Phase 2：规模与指令属性

增强抽取覆盖 239,765 个 method、27,262 个 class，其中 220,036 个 method
有 Code attribute；Code 总长 22,004,483 bytes，classfile 总长
135,020,127 bytes。新增字段包括 method bytecode length、instruction count、
max stack/locals、控制流与异常处理标记，以及 classfile size、constant-pool
entries。调用图仍为相同的 239,765 nodes 与 859,406 resolved call sites。

### Phase 3：Erdős–Kac 式条件正态

以一个 classfile 作为可观测 program，以它引用的不同边界外 method 数作为
组件数，并在 20 个 classfile-size 分位组内标准化。预注册形状判据为
`|skew|<0.2`、`|excess kurtosis|<0.5`、Q–Q `R²>0.99`。

| 组件边界 | classes | 平均组件数 | size–count Spearman ρ | skew | excess kurtosis | Q–Q R² | 判据 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | --- |
| cross-class | 27,262 | 12.569 | 0.751 | 0.660 | 1.472 | 0.975 | 不通过 |
| cross-package | 27,262 | 8.708 | 0.725 | 1.259 | 3.942 | 0.927 | 不通过 |
| cross-module | 27,262 | 3.870 | 0.435 | 2.189 | 9.869 | 0.784 | 不通过 |

因此，当前操作化下的条件组件数保持右偏、厚尾，不支持 Erdős–Kac 式正态
近似。这是对有限 JDK classfile 总体的形状检验，不是对数论定理本身的
检验；classfile 也不等同于独立终端应用。

### Phase 4：组件规模、标识成本与留出净节省

在 47,305 个被精确 `STATIC`/`SPECIAL` 调用的具体方法中，使用次数与 Code
大小几乎没有单调关系（Spearman `ρ=-0.0106`）。以
`max(code_length−3,0)` 作为每次调用的 gross savings，97.84% 的观察满足
粗略的 `savings×8 ≥ ceil(log2(rank))`；但 JVM 调用点实际通过 class-local
constant-pool index 编码，这不是对论文信息论界限的严格验证。

不完备性搜索在 86,055 个无分支、无异常处理的非 synthetic 方法上抽取
4–8 opcode n-gram，并用 package hash 做五折留出。五折均存在扣除定义、
每次引用和引用 class 成本后仍为正的候选；每折最佳 held-out net savings
依次为 4,045、6,844、3,563、7,646、19,517 bytes，中位数 6,844 bytes。
这说明当前 method vocabulary 对该代理编码仍有可压缩片段，但结果仅为
探索性：尚未建模 operands、stack contract、access rules、semantic naming
与 verifier-safe rewriting，不能把 opcode 片段直接宣称为可发布 Java API。

### Phase 5：JDK 17→28 纵向增长

| 快照 | classes | methods | Code bytes | resolved calls | reuse β | R² |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| JDK 17+35 | 26,163 | 222,798 | 19,376,509 | 790,254 | 0.960 | 0.972 |
| JDK 28+13 | 27,262 | 239,765 | 22,004,483 | 859,406 | 0.953 | 0.972 |

按 canonical method key，保留 187,390、增加 52,375、移除 35,408，净增
16,967 个方法。JDK 28 中有 33,250 个新增方法至少被调用一次；保留 method
identity 的 caller 对其中 7,182 个新增 callee 产生 18,643 个调用点。
静态 gross-savings proxy 为 779,663 bytes，但 retained identity 不保证方法体
未改变，该值也不是因果节省量。

这为“有限库在后续快照继续扩展，并采用新增组件”提供了直接纵向证据；两个
版本仍不足以建立组件供给无限、所有新增组件都缩短程序，或最大熵机制。

## 路径入度方法

图的边方向为 caller method → callee method。对每条 pair，multiplicity
等于已解析调用位置数。直接 occurrence 入度为进入节点的 multiplicity
之和。间接路径沿非循环节点传播；同一路径上的 multiplicity 相乘，不同
路线相加。计算使用任意精度整数。

循环边界由多节点强连通分量和 self-loop 节点组成。路径抵达边界节点时
计入该次到达，但不从边界继续传播。这一规则避免把递归 walk 解释为无限
路径，也不枚举强连通分量内部的所有 simple path。

对正路径节点按精确路径数降序排列。在 `log10` 空间分别比较
`A/r` 与 `A/p_r`，其中 `p_r` 是第 r 个素数；两个固定模板各自只
拟合幅度 A。另以自由指数模型 `A/r^β` 估计经验斜率。

## 路径入度结果

| 范围 | 节点数 | 经验 β | Zipf R² | Zipf RMSE | 1/pᵣ R² | 1/pᵣ RMSE |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 全部正值节点 | 138,981 | 3.523 | 0.483 | 1.105 | 0.523 | 1.061 |
| 路径入度最高 1% | 1,390 | 3.416 | 0.474 | 1.092 | 0.547 | 1.014 |

RMSE 的单位为 decade。完整范围内，素数倒数模板比 Zipf 模板的 RMSE
低约 4.0%；最高 1% 范围内低约 7.2%。然而，经验曲线的下降速度接近
`r^-3.5`，与两个固定参考形状都相距较远。

### 参数解释

`βrank = 3.523` 来自自由指数模型 `P(r)=A/r^β` 的双对数斜率。
它表示 rank 增加 10 倍时，路径入度平均约下降
`10^3.523 ≈ 3,335` 倍。严格 Zipf 模型固定 `β=1`，相同情况下只
下降 10 倍。因此，经验分布可以具有近似幂律的 rank 形状，但并不等于
服从 Zipf 定律。

R² 衡量模型在 `log10(path count)` 空间解释的变化比例。Zipf 的
`R²=0.483` 表示固定 `1/r` 形状解释约 48.3% 的对数变化；素数倒数
的 `R²=0.523` 表示解释约 52.3%。在同一总体与拟合方式下，R² 越接近
1 越好，但这两个固定模型都只解释约一半。

RMSE 同样在 log10 空间计算。`1.105 decades` 的误差量级相当于
`10^1.105 ≈ 12.7` 倍；素数倒数的 `1.061 decades` 相当于约
11.5 倍。RMSE 越小越好，倍数表示预测可能高于或低于实际值的数量级。

放开指数后，自由 rank 模型达到 `R²=0.991`、`RMSE=0.147 decades`
（约 1.4 倍）。这支持“经验曲线接近一个较陡的 rank 幂律”，但否定了
指数固定为 1 的 Zipf 解释。素数倒数 `1/p_r` 因
`p_r≈r ln r` 而比 `1/r` 略陡，因此误差稍低；这一点不构成质数
生成机制的证据。

路径入度最高的方法是
`jdk.jdi/com.sun.tools.example.debug.expr.ExpressionParserTokenManager#jjCheckNAdd(I)V`。
它只有 3 个直接 caller pair、22 个直接调用 occurrence，却累积
6,919,543,454,663,852 条直接+间接路径。这表明生成式解析代码中的
分叉和汇合可以支配路径计数；路径入度应解释为结构性路线数量，而不是
独立调用方、运行时执行频率或工作量。

## 结论与限制

在与论文一致的直接静态引用口径下，OpenJDK 方法复用曲线接近 Zipf：
`β=0.953`，固定 `1/r` 的拟合误差较小。直接+间接路径入度则高度集中且
不支持严格 Zipf 分布。两项结果并不矛盾：前者统计组件被直接写入多少个
调用位置，后者统计上游路线的组合数量。素数倒数仅作为路径曲线的负对照；
较小误差不能推出质数规律。

结果限定于精确字节码引用图。反射、运行时构造的 method handle、native
callback 和虚方法的运行时 dispatch 扩展不在图中。循环终止策略是有限
路径计数的一种明确定义，换用 simple-path 枚举或 SCC 内部展开将得到
不同指标。
